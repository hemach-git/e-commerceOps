# Scope Document: Marketplace Catalog Ingestion Engine

## 1. Business problem & objectives
Third-party sellers send listings with messy titles ("Men's Dry-Fit Athletic Gym Shorts w/ Pockets Pack of 2 (Black/Navy, L) - Running Workout"), inconsistent size/colour codes ("Lrg", "Blk/Nvy"), missing attributes and sometimes prohibited claims ("FDA approved", "replica"). Manual clean-up is slow, inconsistent and risky: non-compliant listings reaching shoppers create legal and brand exposure.

**Objectives**
- Turn raw seller listings into clean, structured, correctly categorised drafts automatically.
- Stop non-compliant or incomplete listings before they reach the live catalog, with a clear reason.
- Keep a human in control of what goes live, with a full audit trail.

## 2. Business requirements
**Functional**
1. FR1 Ingest supplier feed rows in batches or one at a time; each run and listing gets a traceable ID.
2. FR2 Clean titles deterministically (junk words, SEO tails, ALL CAPS, emoji, "w/") into a standard template.
3. FR3 Extract variations (sizes, colours, pack count) and normalise supplier codes to canonical values.
4. FR4 Classify into a leaf category of the canonical taxonomy (closed list) with confidence and rationale.
5. FR5 Validate category-required attributes (type, allowed values, ranges).
6. FR6 Enforce compliance rules in Python: prohibited terms (global + category), price, PII, injection.
7. FR7 Route to Draft Catalog or Quarantine with machine-readable reason codes.
8. FR8 Human review: approve drafts to publish, reject drafts/quarantined listings; audited.
9. FR9 Catalog Inspection API: listings, listing detail (raw vs clean vs errors), quarantine by reason, catalog, metrics.
10. FR10 Analytics: KPIs from records, charts, CSV export, plain-English insights.

**Non-functional**
- NFR1 Final decisions are deterministic Python; the LLM only proposes structured data.
- NFR2 LLM provider configurable (anthropic / mock); offline mock for tests, evals and demo.
- NFR3 Referential integrity enforced (FKs on); validated writes.
- NFR4 Structured JSON logs with request_id, duration, status, tokens; secrets/PII masked.
- NFR5 40-listing batch in about 1 second in mock mode (measured).

## 3. Top 3 user journeys
| # | Actor | Trigger | Steps | Outcome |
|---|---|---|---|---|
| 1 | Catalog ops analyst | New supplier feed lands | Ingest page -> Run batch -> review results table | Every listing is DRAFT or QUARANTINED with reasons (measured: 21 / 19 of 40) |
| 2 | Merchandising reviewer | Drafts awaiting review | Review Queue -> compare raw vs clean, attributes, variations, evidence -> Approve | Listing published to live catalog; audit records who/when/why |
| 3 | Compliance / integration engineer | Spike in quarantines | `GET /quarantine?reason=PROHIBITED_KEYWORD` -> `GET /listings/{id}` | Sees exact rule, matched term, LLM raw output vs validated output |

## 4. MVP scope
**In:** synthetic starter DB (8 leaf / 6 root categories, 40 messy listings); deterministic cleaning; LLM classify + extract with strict validation and retry; dynamic attribute validation; compliance rules; draft/quarantine routing; human review + publish gate; audit; FastAPI inspection API; Streamlit UI (ingest, review, catalog, analytics, diagnostics); pytest; golden evals; docs.

**Out:** real supplier connectors, image validation, duplicate/near-duplicate detection, multi-language listings, reviewer authentication/RBAC, editing and resubmitting quarantined listings in the UI, production database.

## 8. Assumptions & limitations
- Starter DB was not provided; it was recreated with the specified schema plus pipeline tables.
- `prohibited_keywords` stored as a JSON list; matched case-insensitively at word boundaries (no fuzzy or semantic matching; obfuscated spellings like "r3plica" slip through).
- The default `mock` provider is a keyword heuristic written alongside the golden set, so the 100% mock eval mainly proves the deterministic layer and plumbing; **real-LLM accuracy must be measured with `python -m evals.run --provider anthropic`** (needs `ANTHROPIC_API_KEY`).
- Injection detection is pattern-based; novel phrasing may pass guardrails, but even then the LLM cannot approve anything: routing and publishing are deterministic.
- Reviewer identity is a typed name (no authentication).
- Re-processing a listing replaces its previous pipeline result (published listings are locked).

## 9. Governance & human review points
- `config.yaml` (model, thresholds, rules) + per-run snapshot (`pipeline_runs.config_snapshot_json`, `logs/run_snapshots/`).
- Audit trail: PIPELINE_ROUTE (system, model, request_id, reason codes), BATCH_RUN, HUMAN_REVIEW (reviewer, decision, note).
- Human review is mandatory before anything is published; the publish gate re-checks status, blocking violations and price.
- Logs are JSON, PII/secrets masked; API keys only from `.env`.
